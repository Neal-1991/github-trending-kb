# 项目整体 Review（2026-09-05）

本轮检查采集、快照、画像、SQLite 重建、通知、Actions、Web 检索与图表以及测试。未修改业务代码，未调用真实飞书或模型服务。复现使用内存 SQLite、临时目录和 mock。

验证：157 项 pytest 通过（1 条依赖弃用警告），Ruff 通过，audit_data 无硬错误、数据库 integrity 为 ok。测试通过并未覆盖以下流程组合。

## 优先修复的问题

### 1. P1：历史日期缺快照时，会把当前榜单写成历史数据

位置：scripts/daily_job.py:87–130。

`--date` 文档定义为回放，但 capture_stage 在指定日期没有快照时直接 fetch_all，再 build_snapshot(date, records)。历史日期显式 refresh 也走相同路径。复现：对 2020-01-01 的缺失快照执行 dry-run，mock 的实时抓取函数仍被调用；非 dry-run 会写入该日期。

建议：日期严格解析；非今天只能回放 canonical/legacy，缺失时明确报错；历史回填另设入口并记录来源。测试缺失历史日、未来日、历史 refresh 均不得调用实时抓取。

### 2. P1：通知失败不会使任务失败，Actions 可能显示成功

位置：scripts/daily_job.py:326–351、428–447、510–519。

飞书 send 返回 ok=False 时，日报和周报仅打印日志，正常返回；main 仍打印 DONE 并以 0 退出。Actions 的 failure() 告警因此无法识别这些失败。已 mock send=(False, 'rejected', None)，确认 push_daily 正常返回 None。

建议：区分未配置、已成功、已发送跳过、发送失败；实际失败写 failed 事件并最终非零退出。周日报可分别尝试、汇总结果后报错，保留成功状态供重试使用。

### 3. P1：刷新缩短榜单后，数据库留下旧榜尾

位置：scripts/daily_job.py:248–262。

main 先从旧 canonical 重建，再捕获刷新版本；profile_stage 只按 (date,list_type,rank) INSERT OR REPLACE，没有删除刷新后消失的名次。旧榜 25 条、新榜 20 条时，21–25 名会残留，聚合和本轮通知读取的 DB 与快照不一致，直到下一次重建才恢复。

建议：在同一事务中删除该日受管真实榜，再完整插入 canonical 全批次，并更新相关派生数据。增加 25→20 条、榜单移除的刷新测试。

### 4. P2：归档后丢失投递去重状态

位置：scripts/delivery_log.py:34–80；scripts/rotate_logs.py:108–126。

轮转把 delivery_log 和 push_log 的过期行移走，但投递查询只读 live 文件，legacy 去重同样不读归档。SQLite 导入归档 push_log 不能解决，因为 push_daily 不查询该表。复现：已发送事件轮转前可查，轮转后 latest_event 返回 None。重新通知 90 天前的日期可能重复发送或重建文档。

建议：去重状态同时查询归档，或长期维护独立的最终状态索引。增加“发送→归档→历史重跑仍不发送”测试。

### 5. P2：历史周报统计没有截止日期

位置：scripts/daily_job.py:391–406。

趋势、首次上榜和画像计数只有 week_start 下限，无报告日期上限。复现：为 2026-08-30 生成周报，插入的 2026-09-05 仓库及 100 星仍进入 top_new，new_repos=1。

建议：日期采用闭区间 [week_start,date]；画像时间采用北京时间半开区间 [周一零点,报告日次日零点)。若要求历史报告内容严格不变，还需保存报告引用的画像版本和周内快照集合。

### 6. P2：堆叠图柱块重叠，语言构成展示错误

位置：web/app.py:644–661。

acc 在每种语言开始时清零，却在季度循环中累加；应当为每个季度累计之前语言的值。目前同一季度不同语言从同一基线绘制，后续季度还受前一季度影响。复现：单季度 A=1、B=1、h=100，两个 rect 均为 y=50,height=50，完全重叠。

建议：按季度外循环、语言内循环，或维护每季度独立累计量。用单季度双色和多季度不同构成校验 SVG 几何位置。

### 7. P2：Actions 摘要通知没有读取现有一句话画像

位置：scripts/daily_job.py:497–503、346。

notify-only 初始化 one_liners={}，仅补新面孔标记，随后把空字典传给摘要卡片。Job A 已生成的画像无法出现在 Job B 的 webhook/降级摘要中。完整单进程模式也只提供本轮新生成的画像，已有画像缺失。

建议：通知阶段从数据库加载当天涉及仓库的 one_liner，与文档模式统一内容来源；测试 capture 与 notify 分开执行的卡片内容。

### 8. P2：今日损坏快照的自愈分支被提前重建阻断

位置：scripts/daily_job.py:87–98、487；scripts/db.py:361–365。

capture_stage 捕获 SnapshotValidationError 并计划重新抓取，但 main 先 rebuild；重建遍历 canonical 时已抛出同样异常，无法进入自愈分支。Actions preflight 的 build_db 还会更早失败。

建议：明确选择 fail-closed 加独立修复命令，或在正式重建前完成今日快照校验与归档修复。不能只单测 capture_stage；应验证 CLI 与工作流顺序。

### 9. P2：仅从榜单获得的元数据在重建后消失

位置：scripts/db.py:359–406；scripts/daily_job.py:231–243。

增量阶段为新仓库写 description/language，但重建只从 canonical 导入趋势数值，缺 API/CSV 元数据的仓库随后仅获空占位行。虽然快照保存了描述和语言，重建未使用；无 Token 或 API 失败时尤其明显。首次运行与次日重建的搜索和语言筛选结果会不同。

建议：按确定日期顺序从 canonical 恢复榜单元数据，优先级低于 API/可靠元数据；增加无 Token 的增量/重建结果等价测试。

### 10. P2：画像积压没有真正的跨日自动补齐

位置：scripts/daily_job.py:153–156、218–238。

超过 80 个的提示声称后续每日任务自动补齐，但候选只来自本日 records。被截断或临时失败后不再上榜的仓库不会再次进入队列。profile_batch 的独立候选又受 core_days 和 README 缓存限制，且不在 daily workflow 内。

建议：持久化任务队列，记录 pending/retry_at/attempts；每天优先当天总榜，剩余额度处理积压；为 no_readme 制定可控复查周期。

## 后续优化建议

- 数据可信度：审计仍发现 34 个 created_at 晚于首次上榜的仓库，85 个重复元数据仓库（61 个字段冲突）。Web 详情未展示身份风险。先对已知异常显示警示并避免作为代表案例，再在有可靠证据时合并；不要按同名猜测仓库身份。
- 新鲜度：本地只有 2026-08-30 至 2026-09-02 四份真实快照。增加“最新采集日期/缺失天数/画像覆盖率”展示和告警；这不能据此断言远端 Actions 已失败，本轮未查询远端运行记录。
- Readiness：get_db 在路由函数执行前连接，缺库异常不会被 readyz 的 try 捕获，返回 500 而非设计中的 503。将连接异常映射到统一不可用响应。
- 性能与一致性：daily 每次全量重建后又全表更新统计、删除重建 FTS；增量 reindex 期间存在索引短暂空缺窗口。先测量请求和批任务耗时，再考虑临时库一次构建替换或事务内增量索引。当前规模无需直接引入新数据库或缓存服务。
- 画像输入一致性：profile_input_hash 包含整个 meta 和 12000 字 README，而实际请求只使用部分字段和 6000 字。共用规范化输入构造函数，避免 fetched_at 等无关字段导致 hash 改变；同时统一 topics 的 JSON 字符串/数组表示。
- 文档：README 仍写历史截至 2026-01、缺口从 2026-02 起，config 已包含 2026-02；详情图提示也硬编码旧缺口。应从实际覆盖区间生成。首页“运行 --dry-run 接入真实榜”的提示亦与零写入语义冲突。
- 测试策略：优先增加以上跨阶段和恢复路径测试；补真实页面脱敏 fixture，避免抓取测试仅验证自造 HTML。现有断言不等同于禁用网络，可增加统一禁止真实网络请求的测试保护。

## 建议实施顺序

1. 修复历史日期写入、通知失败状态和刷新残留，防止源数据污染与静默漏发。
2. 修复归档去重、周报区间、图表、摘要画像以及自愈入口，补端到端回归。
3. 恢复重建元数据等价性、持久化画像队列、展示可信度和新鲜度。
4. 依据实际耗时优化查询/索引，并统一文档与配置口径。

这轮证据支持优先修复流程一致性；现有 FastAPI + SQLite + 文件快照架构可以继续使用。

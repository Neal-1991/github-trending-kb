# 功能设计文档

版本:v1 · 2026-09-06。配套文档:[操作手册](操作手册.md)。

## 1. 系统定位与总体架构

项目目标:用 GH Archive 历史重建榜 + 每日真实抓取榜,构建一个可检索、可追溯的 GitHub 趋势项目知识库,配 AI 生成的项目画像,每日经飞书推送摘要。

架构上把"数据生产"与"本地消费"完全分离:

```
┌─ 云端(GitHub Actions,每天 08:00 北京时间)──────────────┐
│  Job A capture-and-persist:                            │
│    抓取 trending → canonical 快照 → AI 画像 → 元数据    │
│    → 重建数据库校验 → 审计 → 提交数据到 main 分支        │
│  Job B notify:                                         │
│    回放当日快照 → 飞书日报/周报 → 投递日志轮转归档       │
└────────────────────────────────────────────────────────┘
                    │ (数据以 Git 提交形式存在于 main)
┌─ 本地(Windows)────────────────────────────────────────┐
│  同步器 sync_data.py:只读 GitHub,把白名单数据拉到      │
│  data/runtime,校验后原子发布新数据版本                  │
│  Web 服务 web/app.py:读"当前激活版本"的 SQLite,       │
│  提供检索/详情/趋势/浏览页面与 JSON API                 │
└────────────────────────────────────────────────────────┘
```

两条铁律:

1. **本地同步器永远只读**——不执行任何 Git 写操作(git pull/push)、不修改工作区代码与受管数据、不调用模型、不发送通知。
2. **任何同步失败都保留当前可查询的版本**——页面永远可用,失败原因如实展示。

## 2. 云端每日流水线(设计目的与逻辑)

每日任务的职责是"生产可信数据",设计成两个解耦的 Job,通知失败不拖累数据落库。

### 2.1 Job A:capture-and-persist(抓取与落库)

| 步骤 | 内容 | 设计目的 |
|---|---|---|
| 预检 | 全量 pytest + ruff | 代码缺陷不进入生产数据 |
| 捕获 | 抓 GitHub trending 页(total + 4 个语言榜),条数 10~40、stars_today 覆盖率 ≥0.6 校验通过后写 canonical 快照 | 校验不过不产快照,坏数据进不了库 |
| 快照 | `data/daily/snapshots/YYYY/MM/DD.json`,schema v2,含内容寻址 `snapshot_id`(SHA-256) | 快照不可变、可追溯;当日已存在默认回放不重抓;内容损坏自动归档旧版重抓(自愈) |
| 画像 | `pending_queue.json` 持久队列,每日最多 80 个:当天新面孔优先,余量补历史积压;临时错误次日重试,无 README 仓库 30 天冷却 | 画像进度跨日、跨 CI 环境持久,不依赖被清空的缓存 |
| 元数据 | GitHub API 补全仓库信息,`repo_meta_api.jsonl` 按 fetched_at 保留最新一行(与行序解耦的确定性合并) | 同一仓库多行历史观测不产生歧义 |
| 重建 | 从全部 source 全量重建 SQLite(原子:临时库校验通过才替换),trusted 口径聚合、FTS 索引 | 派生库永远可从 source 完整复原 |
| 审计 | `audit_data.py` 检查数据质量矛盾 | 软发现留档,不阻断 |
| 提交 | 提交 `data/daily data/profiles data/raw`,`pull --rebase --autostash` 重试 3 次后推送 | 并发推送安全;**这一步产生的提交就是本地同步的数据源** |
| 失败告警 | 飞书红色卡片附运行日志链接 | 数据没落库必须当天知道 |

### 2.2 Job B:notify(通知)

- 从 `main` checkout Job A 推送后的数据,**回放**当日 canonical 快照(不重新抓取),生成日报(云文档降级链:云文档+链接卡片 → 摘要卡片)与周报(周一),经飞书 webhook 或自建应用发送。
- 每种通知在 `delivery_log.jsonl` 中按事件独立管理状态,语义"至少一次 + 可检测重复",每条携带 snapshot_id 便于识别;`rotate_logs.py` 把过期明细移入 `archive/*.jsonl` 月度归档(重建库时会合并导入,历史不丢)。
- 通知失败发飞书告警并使 Job 失败,但 Job A 的数据已提交;可单独重跑通知。

### 2.3 榜单类型与质量口径

| 类型 | 来源 | 说明 |
|---|---|---|
| `total` / `lang:*` | 每日真实抓取 | 2026-08-30 起 |
| `arch:total` / `arch:lang:*` | GH Archive 历史重建(2021-09 ~ 2026-02) | 按月度事件密度分层:`full`(全可信)/`partial`(仅 Top10 可信)/`degraded`(不聚合);2026-03 起上游事件坍缩,按 degraded 不回填 |
| `star_anomaly` | arch:total 单日星标 ≥15000 判疑似刷星 | `data/raw/star_anomaly_overrides.txt` 人工 include(真实爆发)/exclude(刷星)纠正;flag=1 不参与峰值展示 |

## 3. 本地数据同步器(核心设计)

### 3.1 目标

让本地网页在服务启动后自动与 GitHub 已提交的数据保持一致,同时满足:启动即查(不等网络)、失败可用(保旧版)、Windows 安全(不覆盖被占用的文件)、工作区零污染(不动代码和 Git)。

### 3.2 运行版本存储布局

```
data/runtime/                      # 整个目录 gitignore
  sync.lock                        # 跨进程互斥锁(msvcrt/flock,进程退出自动释放)
  sync_status.json                 # 同步状态(原子写,失败重试)
  active.json                      # 唯一激活指针(原子替换)
  staging/run-<uuid>/              # 候选工作区(校验通过前不生效)
  generations/<generation-id>/     # 已发布的数据版本
    source/raw|daily|profiles/...  # 白名单数据的完整副本
    trending.db                    # 由本机代码从 source 重建的派生库
    manifest.json                  # commit/指纹/文件哈希/构建版本/统计
```

generation-id 形如 `79798dd1-bv1-940f3883`(commit 前 8 位 + 构建版本 + 数据指纹前 8 位)。**不直接替换在用的 SQLite 文件**——版本目录 + 指针切换从根本上避开 Windows 的文件占用问题;Web 每个请求读一次 active.json,整个请求用同一个只读连接。

### 3.3 白名单(同步的数据边界)

| 文件 | 必需性 | 说明 |
|---|---|---|
| `data/raw/repo_meta_snapshot.csv` `repo_meta_api.jsonl` `trends_gharchive.csv` | 必需 | 建库必需源 |
| `data/daily/snapshots/YYYY/MM/YYYY-MM-DD.json` | 必需(≥1 份有效) | canonical 真实榜 |
| `data/daily/trends.jsonl` | 必需 | legacy 兼容源(canonical 优先语义不变) |
| `data/profiles/profiles.jsonl` | 必需 | 画像 |
| `data/raw/star_anomaly_overrides.txt` `data/daily/push_log.jsonl` `data/daily/archive/*.jsonl` | 可选 | 远端没有 → 候选中也没有(不继承旧版残留) |

白名单之外(代码、README 缓存、snapshots/history、身份映射、队列、`.env`、远端 SQLite)一律不同步。注:同步版本不读取工作区 `_missing.txt`(远端本就没有,与 Actions 建库口径一致);`profile_status` 的 no_readme 状态在同步版本中按未知处理,页面不使用该字段,展示无差异。

### 3.4 同步状态机(每次同步的完整流程)

```
获取跨进程锁(被占用 → 直接退出,退出码 3,不写状态)
  → recover_status:以 active.json + manifest 恢复真实状态(进程重启/状态写坏自愈)
  → 清理过期 staging(>24h 崩溃残留)
  → [checking]   解析 main HEAD 的完整 commit SHA(整轮固定用它)
                 拉 git tree(截断 → BFS 逐层补齐;仍截断 → 失败)
                 白名单过滤(必需文件缺失 → 失败)
  → 数据指纹 = sha256(路径+blob sha+大小) 与 active 版本 manifest 对比:
       指纹相同且构建版本相同 → up_to_date(不下载、不重建,仅更新检查时间)
  → [downloading] 逐文件下载:Git blob sha1(带 "blob <len>\0" 前缀)校验
                 单文件/整批大小上限;上一版 blob sha 相同的文件先复制再 sha256
                 复验,不符重新下载(不盲信缓存);网络错误有限重试,限流尊重 Retry-After
  → [validating] CSV/JSONL 完整解析;人工覆盖规则可解析;
                 canonical 快照内容寻址哈希校验;快照缺失 → 失败
  → [building]   用候选 source 由本机代码重建 SQLite(与 Actions 同一套 rebuild)
  → [validating] integrity_check/必需表/FTS 行数=repos 行数/无未来日期/
                 库内最新日期=source 快照日期/首页统计+检索+最新日榜单抽样可执行/
                 当前库已有真实榜时候选不得倒退(REGRESSION)
  → [publishing] 取消点(服务关闭中的任务不得发布)→ staging 整体改名移入
                 generations(Windows 占用短暂重试)→ 原子替换 active.json
                 → 清理老版本(保留 active+上一版;删除失败跳过下次再试)
  → 释放锁;状态每阶段原子落盘
```

**更新判断的口径**:"最新采集日期相同"≠"无需同步"——比较的是**数据指纹**(全部白名单文件内容),所以同日画像/元数据更新也会重建;反之"仅代码提交、数据未变"不下载不重建。

### 3.5 失败语义

所有失败保留旧版本继续服务,状态条显示原因。错误码:`NETWORK_ERROR`(网络)、`HTTP_ERROR`(GitHub 4xx/5xx)、`RATE_LIMITED`(限流,next_check_at 写入服务端 Retry-After)、`TREE_TRUNCATED`、`REQUIRED_FILE_MISSING`、`SIZE_LIMIT`、`HASH_MISMATCH`、`INVALID_SOURCE`(远端数据格式)、`VALIDATION_FAILED`(候选库校验)、`REGRESSION`(远端比本地旧,属合法历史修订场景)、`CANCELLED`(服务关闭)、`TIMEOUT`(超任务时限,默认 900s)、`INTERNAL`。HTTP 错误永远不会被当作"可选文件不存在"。

### 3.6 后台协调器与前端交互

- Web 进程 lifespan 启动协调器:启动即查一次 → 之后每 30 分钟(`DATA_SYNC_INTERVAL_SECONDS`)一查;下载/建库全部在工作线程,不阻塞事件循环。
- 手动触发(`POST /api/sync` 或页面按钮)与自动检查共用同一入口:运行中再触发合并到现有任务,不另起一轮。
- 服务关闭:停止调度,经取消点安全中止,有限等待 5 秒,退出中的任务不发布新指针(候选已清理,下次自动恢复)。
- 前端状态条轮询只读本地 `/api/sync/status`(不访问数据库、不请求 GitHub):运行中 2 秒、空闲 30 秒、页面隐藏暂停;更新完成后给"刷新查看"按钮(保留 URL),**不自动刷新页面**;首次无库时显示准备页,完成后自动进入首页。

### 3.7 安全设计

- 网络只出 `api.github.com`;公共仓库免 Token,`DATA_SYNC_TOKEN` 可选且只入该域名请求头(不写 URL、不入日志)。
- `POST /api/sync` 三重校验:Host 白名单(127.0.0.1/localhost/::1)+ 同源 Origin + 进程内随机 CSRF token;浏览器不能指定任意仓库/URL/输出目录。
- CSP 显式 `script-src 'self'; connect-src 'self'`;前端动态文本全部 textContent;active 指针与清理操作都有路径逃逸检查。

## 4. 本地 Web 功能清单(每项做什么用)

| 功能 | 路径 | 用途与口径 |
|---|---|---|
| 首页 | `/` | 库概况(仓库/画像/天数/日期范围)、最新真实榜 Top10、新面孔、采集新鲜度提示、画像覆盖率、数据缺口提示 |
| 检索 | `/search` | FTS5(trigram,中文可用)+ 短词 LIKE 回退;语言/有画像过滤;真实总数分页;排序模式如实标注 |
| 仓库详情 | `/repo/{full_name}` | 全部元数据 + 五维画像 + 单日星标曲线 + 排名走势(重建榜 trusted 口径,无可信记录回退真实榜) + 身份风险提示(建档晚于上榜) |
| 新面孔 | `/new-faces` | 按首次上榜日(trusted 口径)倒序、自然周分组;语言过滤;周数白名单(4/8/13/26/52) |
| 趋势图谱 | `/trends` | 季度语言构成堆叠图、中坚项目(core_days≥10)、现象级爆发(排除疑似刷星)、各月质量分布 |
| 按日浏览 | `/browse` | 日期轴(重建榜∪真实榜)+ 榜单类型下拉;显式日期无该榜时自动回退并提示 |
| JSON API | `/api/search` `/api/repo/{name}` `/api/day/{date}` | 与 HTML 完全同口径的只读接口 |
| 健康检查 | `/healthz` `/readyz` | 进程存活 / 数据库可查(缺库 503,同步失败但旧库可用时仍 ready) |
| 同步状态条 | 全站 | 见操作手册文案表 |
| 同步 API | `GET /api/sync/status` `POST /api/sync` | 本地状态查询 / 手动触发(202 异步) |

安全基线:数据库只读连接、缺库明确失败不建空库;查询长度/词数限制与转义;SVG 动态文本转义;homepage 仅 http/https。

## 5. 关键设计决策(为什么这样做)

| 决策 | 理由 |
|---|---|
| generation 目录 + active 指针,而不是覆盖 trending.db | Windows 上旧读句柄会阻止替换;指针切换让旧请求自然结束、新请求用新版 |
| 数据指纹而不是 commit SHA 判断更新 | 仅代码提交不应触发重建;同日画像更新必须触发重建 |
| 派生库由本机代码重建,不同步远端 SQLite | 数据与代码版本解耦;不执行远端代码 |
| 不下载 `_missing.txt`、README 缓存 | 远端仓库本就没有(gitignore),同步库与 Actions 建库口径一致 |
| 本地初始构建 `source=local`、commit 为空 | 离线首启可用,且不伪装成 GitHub 版本 |
| 同步器零 Git 写操作 | 本地开发中存在未提交文件也不会与同步冲突 |
| 页面不自动刷新 | 不打断搜索输入;更新完成由用户点"刷新查看" |

## 6. 文件与模块索引

| 模块 | 职责 |
|---|---|
| `config.py` | 路径、榜单定义、密钥、同步配置(全部可在 .env 覆盖) |

| `scripts/rotate_logs.py` | 投递/推送日志月度轮转 |

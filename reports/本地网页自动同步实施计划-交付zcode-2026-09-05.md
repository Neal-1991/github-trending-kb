# 本地网页自动同步实施计划

交付对象：zcode。版本：v1，2026-09-05。

## 1. 目标与交付范围

保留 GitHub Actions 每日采集、生成画像、提交数据、发送飞书日报的现有分工。新增本地网页自动同步能力，让用户启动网页后即可查询，并在后台更新至 GitHub 已提交的最新数据。

用户应获得的体验：

1. 启动 `uvicorn web.app:app --host 127.0.0.1 --port 8000`，有旧库就立即可查询。
2. 服务在后台检查 GitHub。发现新数据时下载、校验、建库，完成后提示更新；不阻塞已有页面和检索。
3. 服务持续运行时每 30 分钟检查一次。页面提供“立即同步”按钮。
4. 网络失败、限流或新数据校验失败时继续使用旧库，展示原因和最后成功同步时间。
5. 电脑关机时，GitHub 每日采集和飞书日报继续运行。本地同步器不负责抓榜、调用模型或发消息。

本轮交付包含：同步 CLI、后台任务、状态 API、网页状态条与按钮、隔离数据缓存、验证与原子版本切换、测试、配置和使用文档。

本轮不做：在线网站部署、手机远程访问、自动升级程序、自动执行 git pull、历史缺口回填、身份数据自动合并、重新生成画像或重发日报。

## 3. 选定的技术方案

### 3.1 数据和程序分开更新

程序仍来自当前项目工作区。同步器从 GitHub 指定仓库读取数据，下载到 gitignore 的独立运行目录，**不覆盖工作区的 `data/raw`、`data/daily`、`data/profiles`，也不改动 `.git` 或业务代码**。

网页读取“当前激活的运行数据版本”中的 SQLite；没有同步版本时兼容现有 `data/trending.db`。现有 `build_db.py`、daily_job、审计与 CI 的默认路径保持兼容。

这样不会因为本地正在开发、存在未提交文件，就发生同步冲突或代码被更新的问题。不能采用下载后逐个覆盖受 Git 管理文件的方式。

### 3.2 一次同步固定一个 Git commit

同步开始时解析 `main` 的完整 commit SHA，再读取该 SHA 对应的数据文件清单。**本次所有文件都按该固定 SHA 下载**，不能每个请求都重新读取 main，否则可能把两个提交的数据混在一起。

v1 可采用 GitHub REST API 获取提交和 Git tree，再按固定 SHA 读取 raw/blob 内容：

- 仓库、分支在后端配置，浏览器不能指定任意仓库、URL 或本地路径。
- Git tree 如返回截断，必须补齐遍历或明确失败，不能拿不完整清单继续建库。
- 利用文件 blob 标识复用未变化文件，仍校验本地缓存内容，不能只相信文件名。
- 若用 Git blob SHA 校验，按 Git blob 编码计算哈希，不得误用裸文件 SHA256 去比较 Git SHA。
- 下载 URL 只指向允许的 GitHub 数据域名；Token 不写进 URL、不返回浏览器、不记录日志。
- 公共仓库允许无 Token；私有仓库/限流时支持可选只读 Token。下载或代理跳转时不得向其他域名转发鉴权头。

v1 不要求修改 Actions 来额外发布数据库，也不下载和执行远端 Python 文件。所有派生库由**本机已安装的代码**构建。

### 3.3 同步文件白名单

按当前重建代码的实际依赖实现白名单，至少覆盖：

| 文件/目录 | 用途与要求 |
|---|---|
| `data/raw/trends_gharchive.csv` | 历史趋势；本项目当前数据集的必需文件 |
| `data/raw/repo_meta_snapshot.csv` | 历史元数据；必需 |
| `data/raw/repo_meta_api.jsonl` | API 元数据；必需 |
| `data/raw/star_anomaly_overrides.txt` | 人工覆盖规则；可选，远端不存在视为空规则 |
| `data/daily/snapshots/YYYY/MM/YYYY-MM-DD.json` | canonical 真实榜；至少应有一份有效快照 |
| `data/daily/trends.jsonl` | legacy 兼容源；必需，canonical 优先语义不变 |
| `data/profiles/profiles.jsonl` | 画像；必需 |
| `data/daily/push_log.jsonl` | 重建 push_log 表；可选 |
| `data/daily/archive/*.jsonl` | 归档 push_log；可选，过滤混存事件的现有语义不变 |

不下载 `.env`、代码、README 缓存、诊断文件、profiles 批处理队列、快照 history、`pending_queue.json`、远端 SQLite。投递日志和身份映射等未参与网页建库的数据不纳入 v1；如后续功能确需读取，再显式加入白名单及测试。

必需文件在固定 SHA 中不存在：同步失败并保留旧版；可选文件不存在：候选版本中不存在该文件，不继承旧版残留。HTTP 403、超时、下载错误不能当作“可选文件不存在”。

## 4. 本地目录与版本切换

建议布局：

```text
data/runtime/                       # 整个目录加入 .gitignore
  sync.lock                         # 跨进程同步互斥
  sync_status.json                  # 运行状态，原子写入
  active.json                       # 唯一激活指针，原子替换
  staging/<run-id>/                  # 尚未通过校验的候选
  generations/<generation-id>/
    source/raw/...
    source/daily/...
    source/profiles/...
    trending.db
    manifest.json                   # commit、文件指纹、构建版本、校验摘要
```

`generation-id` 不能仅等于 commit SHA：同一份数据在本地建库版本升级后也可能需要重建。由数据指纹与显式 `DB_BUILD_VERSION` 等确定构建身份，或使用唯一 ID 并把这些信息写入 manifest。

推荐完整流水线：

```text
获取同步锁
  → 解析远端 SHA 与文件清单
  → 判断数据指纹和本地建库版本是否变化
  → 创建独立 staging
  → 下载/复制所需文件，校验完整性
  → 解析源数据、校验 canonical 哈希
  → 用显式 source 路径构建候选 SQLite
  → 数据库完整性、schema、FTS 与关键查询验证
  → 关闭候选 DB 写连接
  → 将 staging 移入唯一 generation 目录
  → 原子替换 active.json
  → 标记成功并释放锁
```

关键约束：

- `active.json` 只引用运行目录内已通过验证的 generation，不允许路径逃逸。
- 每个 Web 请求打开数据库时只解析一次指针，整个请求使用同一只读连接；不跨版本拼接查询。
- **不要直接替换正在使用的 SQLite 文件**。Windows 可能因读句柄占用而拒绝替换；版本目录加指针可以避开这个问题。
- 切换前故障，active 不变；切换后状态文件写失败，下次从 active/manifest 恢复真实状态，不回退至旧版。
- 老请求允许继续读取旧 generation，新请求读取新 generation。
- v1 保留当前版本和上一版；更老版本延后清理。删除失败（如 Windows 占用）只跳过重试，不影响同步。不能删除 active、上一版或在用 staging。
- 每次清理先校验解析后的绝对路径仍在 runtime 管理目录内，禁止递归清理用户工作区。

### 4.1 建库接口必须显式传入路径

当前 `scripts/db.py`、snapshot_store 使用 `from config import ...` 的模块全局路径。在后台同步线程中修改这些全局变量会影响 Web 请求、测试或其他任务，禁止这么做。

建议新增不可变路径配置对象 `SourcePaths`，至少包含 raw、daily、profiles、readmes；重构为：

```python
rebuild(db_path=None, close=None, *, sources=None)
```

`sources=None` 保持现有行为；同步传入候选 source 目录。沿 `_import_sources`、人工覆盖、snapshot 遍历等调用链完整传参。同步版本没有 README 缓存，不能借用工作区 `_missing.txt` 污染远端版本；相关缺失状态按未知处理，不影响已有画像。

Web 的运行库选择与 scripts 的默认 DB 路径分离。已有 `rebuild()` 调用不能因为启用了 Web 同步就写入当前激活的运行版本。

## 5. 更新判断、校验与异常语义

### 5.1 更新判断

- “最新采集日期相同”不等于“无需同步”：同日画像、元数据、人工覆盖仍可能更新。
- 远端 commit 未变且本地构建版本未变：直接结束。
- commit 变化但白名单文件指纹未变：只更新最近检查信息，不重建数据库。
- 任一白名单内容变化或 `DB_BUILD_VERSION` 变化：构建新候选版本。
- 必需文件缺失、源格式不兼容、校验失败均不能发布候选。
- 设置单文件与总下载大小上限、请求超时、总任务时限；初始建议 64 MiB/文件、512 MiB/整批、15 分钟/任务，配置可调整。

### 5.2 验证至少包括

1. 文件清单仅含白名单路径、无绝对路径/`..`/符号链接。
2. 文件实际大小与 blob 内容校验；CSV/JSONL 可完整解析。
3. canonical schema、文件日期与内容日期、snapshot_id 校验。
4. `integrity_check`、必需表、FTS 行数与 repos 行数一致。
5. 数据库有真实榜且最新日期与候选 source 一致，无未来日期。
6. 查询首页统计、一个搜索样例和最新日榜单可成功。
7. 当前库已有真实榜时，远端候选的最新真实榜日期不得静默倒退；v1 报“远端数据较旧”，保留当前库。合法历史修订不要求总记录数单调增长。

旧历史重复元数据、身份矛盾、疑似刷星等当前审计的质量发现仍可存在，不能把已知软发现全部提升成阻止同步的硬错误。

### 5.3 状态模型

建议阶段：`idle/checking/downloading/validating/building/publishing`。

建议结果：`never_synced/updated/up_to_date/failed/disabled`。

状态记录至少包含：

- `phase`、`last_result`、`running`。
- `last_checked_at`：实际完成远端检查的时间。
- `last_success_at`：本地完整数据版本已确认可用的时间；无变化检查也可以更新。
- `last_updated_at`：实际切换 generation 的时间，不能在无变化检查时伪造更新。
- `remote_commit`、`active_commit`、`active_generation`。
- `active_latest_date`：当前激活数据库的数据日期，不是刚发现但尚未下载的远端日期。
- `last_error_code`、安全可读的 `last_error_message`、`next_check_at`。

失败时保留旧库的 active_commit/date/last_updated_at，不把“同步失败”显示成“没有数据”。后台错误必须落状态并能由页面和 CLI 看到，不得只 print 或静默吞掉。

网络失败做有限次重试；遇到限流尊重服务端返回的重试信息，并安排后续检查，避免密集重试。页面状态轮询只读本地状态，绝不能每次轮询就请求 GitHub。

## 6. 触发、并发与 Web 接入

### 6.1 后台任务

- 用 FastAPI lifespan 启动并管理后台协调器，服务启动后立即安排一次检查；不能在模块 import 时请求网络。
- 网络/文件下载/SQLite 重建不能在异步事件循环中直接阻塞执行，应交给受管理的线程或任务执行器。
- 每 30 分钟安排检查；自动与手动触发共用同一互斥入口。
- 同步运行中再触发，返回当前任务，不另起一轮。
- 同时防止 CLI、服务重启或多个进程并发发布：使用能随进程退出释放的跨进程锁，不能只有线程锁或“文件存在即锁住”的永久锁。
- 关闭服务时停止安排新任务，有限等待或安全中止候选任务；正在退出的任务不得继续发布新指针。为下载与建库设置阶段取消点。
- v1 默认单 Web worker，不依赖多 worker 部署；仍需防止开发重载或 CLI 造成的并发。

### 6.2 API

| 接口 | 语义 |
|---|---|
| `GET /api/sync/status` | 返回当前本地同步状态，无数据库依赖；即使缺库也返回可读状态 |
| `POST /api/sync` | 异步触发一次检查，立即返回 202 与状态/任务标识；正在同步则合并到现有任务 |

POST 不等待整批同步完成；建议在本地环境 1 秒内响应。状态查询只访问内存/状态文件，不能新建 SQLite 或访问 GitHub。

保留 `/healthz` 进程健康检查。`/readyz` 检查当前实际可查询的库；缺库时 503，同步失败但旧库可用时仍 ready。

安全边界：默认监听 `127.0.0.1`。不开放 CORS。写接口采用同源校验加本地 CSRF token，覆盖跨站表单/脚本触发，不能靠“只在 localhost”省略保护；测试不同 Origin、错误 token 和不允许的 Host。浏览器请求不能提供 GitHub URL 或输出目录。

### 6.3 首次启动、旧库与离线行为

1. 有有效 active：立即服务该库，后台检查更新。
2. 无 active、有旧 `data/trending.db`：立即兼容读取旧库，后台同步。
3. 两者都没有、工作区有 source：后台优先尝试从工作区 source 在运行目录构建可用初始版本，再检查远端；这一步不修改工作区 source。
4. 没有任何可用库：首页显示“正在准备数据”及同步状态，不能展示原始异常；查询 API 暂回 503。完成后可刷新使用。
5. 离线且没有 source/库：显示“尚无本地数据，请联网后重试”，保留手动重试入口。

初始本地版本的 manifest 标记 `source=local`、commit 为空，不能伪装成某个 GitHub SHA。

## 7. 网页交互

在全站公共布局增加轻量同步状态条，至少显示：

- 数据更新至 YYYY-MM-DD。
- 最近成功同步时间。
- 正在检查/下载/建库/已是最新/更新完成/同步失败。
- “立即同步”按钮，运行中禁用并显示当前阶段。

失败文案例子：`同步失败：网络暂不可用。当前仍可查询截至 YYYY-MM-DD 的数据。`

成功文案例子：`新数据已就绪，更新至 YYYY-MM-DD。刷新查看。`

v1 **不要无条件自动刷新页面**，避免打断搜索或丢失输入。提供刷新按钮并保留当前 URL/查询参数；用户下次导航自然使用新版本。首次准备页没有可用数据时，可在成功后自动进入首页。

状态轮询建议运行中 2 秒、空闲 30 秒；页面隐藏时暂停或放缓轮询。轮询只访问本地 status。

新增 `web/static/sync.js`，使用同源外部脚本；现有 CSP 仅需显式补充合理的 `script-src 'self'`/`connect-src 'self'`，不要为了方便启用任意外域或 inline script。动态错误文本用 textContent，不用 innerHTML。

日期语义必须区分：

- “最新采集日期”：榜单本身的 date。
- “最近检查时间”：检查 GitHub 的时间。
- “最近更新成功时间”：激活新版本的时间。

远端也未更新至今天时，应显示“与 GitHub 已同步，数据截至某日”，不要误报本地同步失败。北京时间 08:00 是计划触发时间，不代表日报或数据必须准时到达。

## 9. 按顺序实施与阶段验收

### 阶段 0：保存和发布现有修复

完成第 2 节的工作区确认、203 项基线回归、独立提交及安全整合远端数据。先让云端使用现有修复，不把本次开发与旧缺陷混在一个提交里。

### 阶段 1：路径隔离与运行版本存储

实现 SourcePaths、显式建库输入、runtime generation 与 active 指针、Web 只读库解析。此阶段可完全离线。

验收：从两套临时 source 分别建库不会串数据；切换后新请求读新版、旧连接仍可完成；默认 build_db/daily_job/tests 不受影响；Windows 无需覆盖已打开的 DB 文件。

### 阶段 2：同步 CLI

实现固定 SHA、白名单下载、缓存复用、验证、失败保留旧版、互斥、状态持久化、构建版本判断。

验收：一条 CLI 命令能使运行库更新；重复运行无变化不下载大文件、不重建；任何阶段故障均有可读错误及明确退出码。

### 阶段 3：后台与页面

接入 lifespan、周期检查、手动触发 API、状态条、缺库准备页、刷新提示和 CSRF 保护。

验收：启动和查询不等待网络；手动触发及时响应；运行中重复点击不重复下载；失败保持旧库可查询。

### 阶段 4：集成验证与交付

运行全量回归、Ruff、diff 检查，Windows 实机验证。用真实远端做一次**只读数据同步**并核对日期/commit，确认不调用 GLM、不发送飞书、未修改受管 source。

准备提交、README、实施记录、测试结果与回滚说明；最终交付不应只有截图或口头“完成”。

## 10. 必须覆盖的测试清单

| 场景 | 预期 |
|---|---|
| 有旧库，GitHub 连接慢 | 页面仍立即可查；后台显示 checking |
| 新 commit、新快照 | 验证后激活，查询日期更新 |
| 同日期更新画像/元数据 | 仍更新，不能只比较日期 |
| 仅代码提交、数据未变 | 不重建数据版本 |
| commit 未变，构建版本变化 | 用本地新建库逻辑重建 |
| 下载过程中 main 再变化 | 本次所有下载仍使用最初 SHA |
| tree 截断/必需文件缺失 | 补齐或失败，旧库不变 |
| 可选文件从远端移除 | 候选中同步移除，不残留旧覆盖规则 |
| CSV/JSONL 损坏、hash 不符、schema 不兼容 | 不激活候选 |
| HTTP 403/429/500、超时、断网 | 有限重试和可读状态，旧库继续查询 |
| 本地缓存内容被破坏 | 校验发现并重新下载或失败，不盲信缓存 |
| 校验/建库/发布前异常 | active 指针和旧库不变 |
| 指针发布后状态写入失败/进程重启 | 从 active/manifest 恢复，识别新版已生效 |
| 同步与查询同时发生 | 单请求只使用一个版本，无缺表/空 FTS |
| Windows 旧库有打开连接 | 新版本仍可发布，清理旧库失败可延后 |
| CLI 与 Web 同时触发 | 只有一个同步发布者 |
| 首次启动且无库 | 准备页可访问；status 不依赖 DB；成功后可查询 |
| 首次启动且离线 | 有工作区 source 则可离线建库；否则明确无数据 |
| 自动同步关闭 | 不出网，手动入口明确禁用，旧查询正常 |
| 跨站 POST、错误 token/Host | 被拒绝，不启动任务 |
| 成功同步前后工作区比对 | 代码、tracked data、.git、.env 不变 |
| 程序关闭时任务未完成 | 停止发布，候选可安全恢复/清理 |

测试外部请求全部 mock，保持现有禁止真实 requests 网络的保护。专门测试后台生命周期，避免现有 TestClient 用例在启动时偷跑真实同步。真实网络验收作为人工命令独立执行，不混入 pytest。

## 11. 最终验收口径

用两个可控数据版本完成以下演示：旧版只有 D 日，新版增加 D+1 日并更新一个画像。

1. 先启动旧版网页，确认能搜索和查看 D 日。
2. 触发同步，新版准备期间旧查询持续可用。
3. 同步完成提示 D+1；刷新后新榜单与新画像同时出现，active_commit 与验收远端一致。
4. 再同步一次，不重复下载未变文件、不重建。
5. 断网后同步失败，D+1 数据仍可查询。
6. 用损坏候选重复验证，不能破坏 D+1。
7. 工作区代码和受 Git 管理的数据文件没有同步造成的修改。
8. 全量 pytest 不低于现有覆盖，Ruff 通过；记录实际测试数、耗时、Windows 验证结果。

回滚方法：关闭 `DATA_SYNC_ENABLED` 可停止同步而保留查询；运行版本出问题时，将 active 指向已验证的上一 generation（通过受锁保护的维护命令），或显式恢复到工作区数据库模式。不得把“删掉全部 data”作为回滚步骤。
